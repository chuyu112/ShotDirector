## 2. 产品定位

“镜导”是一套本地 AI 导演工作台。核心目标不是一次生成几十个镜头，而是让每个镜头的事实、人物、场景、动作、连续性、导演站位、临时分镜图和最终视频提示词处在同一条可审核、可追踪、可反推的链路上。

核心工作流：

1. 设定项目级“全局事实”。
2. 载入结构化脚本、Markdown、纯文本或漫画。
3. 自动拆出 Shot，并保留原文或原画格证据。
4. 在单个 Shot 中审核人物、物品和场景、剧情、动作、连续性、美术风格。
5. 用 TOP VIEW 和 3D 白模检查人物、车辆、摄影机和动作路径。
6. 独立盖章批准脚本；批注成功不等于批准。
7. 生成临时分镜参考图，或直接上传已有参考图。
8. 编译 Seedance 视频提示词和参考资产清单。
9. 把确认过的修改反推到脚本源数据和资产账本。

## 3. 技术架构

### 3.1 运行组成

- 前端：React 19 + TypeScript + Vinext/Vite。
- 本地桥接：Node.js HTTP 服务，默认监听 `127.0.0.1:4317`。
- 页面：默认监听 `http://localhost:3000`。
- 3D：Three.js，用于导演白模、人物姿势、车辆和摄影机关系。
- GPT / Codex：桥接进程调用随项目安装的 `@openai/codex` CLI，执行结构化整理、批注和漫画分析。
- LibTV：桥接进程只通过官方 `libtv` CLI 操作登录、画布、上传、节点和模型，不自行拼接私有 HTTP 请求。
- 视频工具：Python + FFmpeg，用于每秒抽帧、接触表和媒体信息。

启动 `npm run dev` 会并行启动页面和桥接服务。

### 3.2 主要模块

| 文件/目录 | 职责 |
| --- | --- |
| `app/page.tsx` | 主工作台、状态、逐镜审核、盖章、提示词、资产台、桥接调用和本地持久化 |

### 3.3 桥接接口概览

桥接仅接受本机 `localhost` / `127.0.0.1` 来源，并使用页面启动时取得的配对令牌。主要接口：

- `GET /health`：连接状态、配对信息和能力检查。
- `POST /load-script`：自然语言或文本脚本结构化。
- `POST /annotations`：单镜批注。
- `POST /annotations-batch`：多镜批改。
- `POST /global-annotations`：全局设定批注。
- `POST /source-global-settings`：保存全局设定源文件。
- `POST /source-shot`：把当前 Shot 写回源数据。
- `POST /recover-annotation-output`：恢复已生成但页面未收到的批改结果。
- `POST /generate`：调用 LibTV 生成分镜图。
- `POST /generate-asset`：通过 LibTV 生成资产图。
- `POST /generate-asset-gpt`：通过 GPT Image Generation 生成资产图。
- `POST /libtv/login`：启动 LibTV 登录流程。
- `POST /media-upload`：流式保存漫画或视频素材。
- `POST /media-analyze`：启动漫画拆解或视频拉片。
- `POST /media-recover`：恢复媒体任务。
- `GET /media-job-result`：读取媒体任务进度和结果。
- `GET /media-panel/...`：读取漫画分格截图。
- `GET /media-source/...`：读取原素材。
- `GET /media-preview/...`：读取视频接触表等预览。
- `GET /job-result`：恢复生图等后台任务。
- `GET /artwork/...`：读取本地生成结果。

## 4. 数据保存在哪里

### 4.1 浏览器数据

浏览器 `localStorage` 保存：

- 当前脚本与草稿命名空间。
- Shot 批注、审核状态和版本轨迹。
- 全局设定草稿。
- 自定义 Lib Image / 视频提示词。
- 当前模型、参考数量和界面进度。

浏览器 `IndexedDB` 保存：

- 已生成或锁定的分镜图。
- 3D 白模导出的 PNG。
- 与草稿绑定的较大二进制资产。

浏览器数据不会随源码 ZIP 自动迁移。如果需要保留某台电脑上的审核进度，必须增加“导出项目包/导入项目包”，或者人工导出对应浏览器配置。当前交付包特意不携带这些数据。

### 4.2 本地服务数据

桥接在运行时创建：

- `work/shotdirector-responses/`：GPT / Codex 输出和恢复文件。
- `work/shotdirector-artwork/`：生图结果。
- `work/shotdirector-whitebox/`：白模临时文件。
- `work/shotdirector-media/uploads/`：上传素材副本。
- `work/shotdirector-media/jobs/`：漫画拆解和视频拉片任务。
- `work/libtv-bridge/state.json`：共享 LibTV 工作区/画布状态。

这些目录未放入迁移 ZIP，避免把旧漫画、生成内容和账号相关状态带到新电脑。

### 4.3 源文件回写

- Shot 确认写回 `app/storyboard-data.ts`。
- 全局设定写回 `app/global-settings.ts`。
- 批注完成并不自动批准；只有独立“签字盖章”才改变审批状态。
- 页面状态写回与源文件回写是两条链路，失败时必须清楚提示，不能假装已同步。

## 5. 新电脑安装步骤（Windows）

### 5.1 必备软件

建议：

- Windows 10/11 x64。
- Node.js 22.13 或更高；本机验证版本为 Node 24.16.0。
- npm；本机验证版本为 npm 11.13.0。
- Git（继续版本管理时需要）。
- Python 3（视频拉片需要）。
- FFmpeg（视频拉片需要；也可以用 Codex 环境内置的 FFmpeg）。
- LibTV CLI（Lib Image / General image Pro / Seedream 出图需要）。
- 可用的 Codex 登录或 API 环境。

### 5.2 解压与安装依赖

把 ZIP 解压到不含权限限制的目录，例如：

```powershell
cd 'D:\AI-Director\镜导 ShotDirector'
npm ci
```

不要复制旧电脑的 `node_modules`；用 `npm ci` 根据 `package-lock.json` 重装，避免二进制依赖与新电脑不兼容。

### 5.3 安装 LibTV CLI

官方 Windows 安装方式：

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
Invoke-WebRequest `
  -Uri "https://liblibai-web-static.liblib.cloud/cli/latest/install-libtv-cli.ps1" `
  -UseBasicParsing | Invoke-Expression
```

默认安装到：

```text
%USERPROFILE%\.libtv\libtv.exe
```

重开 PowerShell 后检查：

```powershell
libtv --help
libtv login web --open
libtv account info
libtv account list
```

如果登录到了错误账号：

```powershell
libtv account list
libtv account use <accountId或精确账户名>
libtv account info
```

镜导桥接默认直接寻找 `%USERPROFILE%\.libtv\libtv.exe`。如果放在别处，启动前设置：

```powershell
$env:LIBTV_BIN = 'D:\Tools\libtv.exe'
npm run dev
```

### 5.4 启动

```powershell
npm run dev
```

打开：

```text
http://localhost:3000
```

正常状态应看到页面和桥接均启动，且页面显示 GPT/桥接已连接。桥接默认地址：

```text
http://127.0.0.1:4317
```

### 5.5 第一次运行验收

依次验证：

1. `npm test` 能完成构建并通过测试。
2. 页面可打开，浏览器控制台没有 Runtime Error。
3. `/health` 返回正常，页面显示桥接已连接。
4. 能新建一个空白草稿，不出现旧漫画数据。
5. 选择一张测试漫画后，队列只出现这一张。
6. 填写故事背景和最终成片风格后，“开始拆解”可点击。
7. LibTV `account info` 是正确账号。
8. 用一个低成本测试提示词验证生图调用；避免未确认账号时直接运行正式任务。

## 7. 业务规则与不可混淆项

### 7.1 审批

- 批注已上传、GPT 已修改、源文件已回写，都不等于审批通过。
- 每个 Shot 必须单独签字盖章。
- 生图不应阻塞进入下一 Shot；同一 Shot 可多次生成候选图。
- 提示词或上游数据变化后，旧确认结果应标为过期，而不是静默沿用。

### 7.2 美术风格分层

- `artStyle` 是最终视频成片风格，来自项目/脚本，例如“昭和 60 年日本真人电影化”。
- 临时分镜图可用赛璐璐导演工作图，目的只是锁定剧情、场景、站位和动作。
- 临时分镜画风不能反推覆盖最终视频画风。
- 静态生图提示词与视频提示词不能完全复制，应分别编译。

### 7.3 Seedance 限制

- Seedance 2.0：单镜 4–15 秒，最多 9 个全能参考。
- Seedance 2.5：单镜 4–30 秒，最多 50 个全能参考。
- 人物、关键场景和关键道具默认进入参考候选；普通物品不应无条件占参考位。
- UI 必须显示参考计数和超限原因。

### 7.4 漫画转分镜

- 漫画项目必须建立新草稿命名空间，不能覆盖已经存在的剧集。
- 每个 Shot 保留 `sourcePanels`、分格截图和 `sourceText`。
- 单个漫画格不机械等于一个镜头；按地点、时间、摄影机意图和连续动作合并/拆分。
- 漫画事实与导演建议必须分开存储。
- OCR 不可靠的文字标为“疑似”，不得擅自补对白。
- 人物、场景和关键道具要自动转为资产项并生成独立资产提示词。

## 9. 常见故障

### 页面能打开但 GPT 很慢

本地页面不代表模型在本地推理。桥接仍要通过 Codex/GPT 网络请求；模型排队、上下文过长、结构化输出重试和网络重连都会增加耗时。应优先缩短单次输入、分批处理、缓存不变的全局设定，并显示真实任务阶段。

### `Invalid schema for response_format`

检查 `scripts/*.schema.json`：每个 `properties` 字段必须具有合法 `type`，对象的 `required`、`additionalProperties` 和数组项也要完整。修复后先用一个最小请求测试，再运行正式漫画任务。

### `Cannot read properties of undefined`

旧草稿结构缺字段或迁移后字段为 `undefined`。渲染层对数组使用 `?? []`，对字符串使用 `?? ""`；数据迁移必须先标准化，不能在 JSX 中直接 `.length` 或 `.trim()`。

### 点击“进入分镜”无效

检查：

- 结果中 Shot 是否有稳定唯一 ID。
- `sourcePanels` 是否能找到 `/media-panel/...`。
- 是否成功创建独立 draft 查询参数。
- 浏览器是否阻止新标签页。
- 历史映射是否把多个镜头错误合并到同一个序号。

### LibTV 生图失败或找不到画布

```powershell
libtv account info
libtv workspace list
libtv project list
```

确认账号、工作区和画布。镜导会复用 `work/libtv-bridge/state.json` 中的共享画布；迁移包不带该文件，新电脑首次生成时需要重新建立绑定。

### 视频拉片失败

检查 Python、FFmpeg、文件扩展名和路径权限；然后查看桥接日志与 `work/shotdirector-media/jobs/<任务ID>`。视频可能很大，勿把 `work` 整目录提交到 Git。

## 10. 已知技术债与风险

1. `app/page.tsx` 超过 240 KB，状态与业务耦合过重；应拆分 store、API client、workflow service 和页面组件。
2. `scripts/shotdirector-bridge.mjs` 超过 140 KB；应拆成 auth、revision、media、LibTV、filesystem 和 job recovery 模块。
3. `app/manga-panel-mapping.mjs` 含历史草稿特殊修复与硬编码映射，可能导致新漫画被旧逻辑污染。
4. 清空媒体任务缺少服务端级联删除，页面清空与磁盘清空语义不一致。
5. 草稿持久化分散在 localStorage、IndexedDB、源 TS 和 `work`，缺少统一项目清单和事务边界。
6. Shot 重编号曾引发内容、资产和图片串镜；业务主键必须与显示序号分离。
7. GPT 批注链路较慢，且全局修改、源文件回写和提示词刷新目前不是严格原子操作。
8. 生成图、白模、脚本和视频提示词的版本依赖需要更明确的“已过期”计算。
9. 前端 bundle 偏大，需要对 Three.js / 白模编辑器和媒体实验室做懒加载。
10. README 在部分 Windows PowerShell 读取环境中可能显示乱码；编辑和打包必须统一 UTF-8。

## 11. 推荐的下一步开发顺序

1. 建立统一 Project Manifest，集中记录 draft、Shot、资产、证据、版本和文件位置。
2. 实现“删除项目/草稿”服务端接口，预览范围、二次确认并级联删除。
3. 把稳定 `shotUid` 与可变 `displayNumber` 分离，禁止使用数组下标作为资产主键。
4. 完成漫画导入事务：预览 → 人工校验 → 一次提交 → 独立命名空间。
5. 建立全局设定传播器和脏数据图，只重编译真正受影响的 Shot 和提示词。
6. 把提示词编译改为确定性本地模板；只让 GPT 处理需要语义判断的内容。
7. 增加项目包导入/导出，覆盖 localStorage、IndexedDB、源数据和媒体证据。
8. 最后再优化批注对话体验和多任务并发。
